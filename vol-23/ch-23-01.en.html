1. Overview

Core in five points. Read these first; each links to the section that develops it.

  1. The engine is event-driven: the clock jumps from one state change to the next, and time-stepped models run inside single events where motion is continuous. Fifteen events reproduce DT17's 1564.06 s cycle exactly; a 1 s loop needs 1565 steps and is still 0.94 s off (section 4.1).
  2. Events are ordered by time, priority and insertion sequence, so equal inputs give equal event logs; a list order is an input (section 4.2).
  3. Adapters mirror FMS, AMS, ADS, VCS, independent safety functions, onboard systems, manned-vehicle devices and people; they communicate only through events, and authority boundaries are inputs an adapter does not have (section 4.3).
  4. A run is reproducible from its configuration and identified by its run hash; two results are compared only when their summaries match, and different seeds are replications, not changes (section 4.6, section 8.1).
  5. The models give different "baseline" numbers for stated reasons: the 1564 s cycle, the fleet model's 184,140 t and the live world's production differ by fleet, queues, acceleration and traffic, not by error; every number is quoted with its model conditions (section 4.10).

Reading order. Core path: sections 1 and 2, 4.1 to 4.3, 4.6 and 4.10, the shared timeline in 6.1, the run summary and procedure in 8.1 and 8.3, and 15. Detail sections (adapter protocol, dependency graph, scenario runner, the Engineering view, verification, mistakes, worked examples) and reference sections (terms, requirements, labs, sources) are folded in the article and open from their summary line or from any link into them.

1.1 Why this chapter matters

On Monday the AHS Controller and the Pit Supervisor want to rehearse a cancellation before a planned C01 chute inspection: the FMS cancels M-20481 while DT17 is loaded on R01, and the crew should see, second by second, what the FMS, the AMS and the truck do and when each of them reports. They send the request to the site engineer, who runs the integrated simulator. The same morning the planner shows two runs of "the baseline shift" at the weekly review: one gives 184,140 t, the other 184,360 t. Nobody can say whether the 220 t difference means anything, because nobody can say how the two runs differ.

Both requests raise the questions of this chapter. How does a simulator built from twenty-two volumes of separate models advance time, and in what order does it process two things that happen at the same instant? How are its parts cut so that the AMS model cannot override the truck? What must be written down so that a run can be repeated exactly and two results compared? And what must a request contain so that the engineer can run it without a second conversation?

This chapter covers:

  • the discrete-event engine of ahs_sim.engine (simulation clock, event queue, deterministic tie-breaking) and why it suits the reference mine better than a fixed time step;
  • the module boundaries of the simulator, which mirror FMS, AMS, ADS, VCS, independent safety functions, onboard safety-related systems, manned-vehicle devices and people, and the adapter interface every earlier module uses;
  • the module dependency graph: acyclic, free of visualisation imports, with one deferred function-level cycle reported;
  • reproducibility: configuration, seed, versions and run hash, and the rule for comparing two runs;
  • the scenario runner and the operations "scenario request"; people as scripted decision policies.

1.2 Learning objectives — Engineering

After this chapter an engineering reader will be able to:

  1. Explain the discrete-event simulation model (simulation clock, event queue, deterministic tie-breaking) and justify it against a fixed time-step design for the reference mine.
  2. Design the module boundaries of the integrated simulator so that they mirror FMS, AMS, ADS, VCS, independent safety functions, onboard safety-related systems, manned-vehicle devices and people, and show that the dependency graph is acyclic and free of visualisation imports.
  3. Specify the configuration, seed and version metadata that make a run reproducible, and verify that two runs with identical inputs produce identical event-log hashes.
  4. Define the adapter interface (inputs, outputs, emitted events) every earlier-volume module implements, and show how a module is replaced by a stub for testing.

1.3 Learning objectives — Operations

After this chapter an operations reader will be able to:

  1. State which operational questions the simulator can help answer (sequence, timing, relative throughput impact) and which it cannot (absolute safety assurance, real-mine forecasts).
  2. Write a scenario request for a rehearsal (scenario ID, shift, fleet state, injected events, outputs wanted) that an engineer can run without further clarification.
  3. Explain how roles (AHS Controller, Pit Supervisor, Shovel Operator, ERT) are represented as scripted decision policies and why simulated human response times are assumptions [A].
  4. Check from two run summaries (configuration, seed, versions, KPIs) whether their results are comparable before using them in a discussion.

2. Operational motivation: the problem at the reference mine

Every volume of this handbook added a model to ahs_sim: DT17's 1564 s cycle on M-20481 (ch-01-01), the FMS dispatching 37 producing trucks (ch-01-07), AMS reservations and permissions (Volumes 02 and 10), a truck stopping on its grade (Volumes 05 to 08), the loss of CT3 (Volume 11), event logs and KPIs (Volume 22). Each answers its own chapter's question. None alone answers the questions of section 1.1: the cancellation involves three elements and a person, and a CT3 outage matters because the AMS, the trucks and the controller react to it at different times. The models must run together, on one clock, writing one log, under one configuration.

Integration brings three risks that the separate models did not have.

Order. Two models may act at the same instant (a truck reaches a queue as the shovel finishes a load). If the simulator does not define which goes first, two runs of the same input can differ for no stated reason.

Authority. A simulator that lets the FMS model stop a truck, or the AMS model override a vehicle-side stop, teaches the wrong architecture; its parts must respect the boundaries of ch-01-04.

Trust. A result that cannot be reproduced cannot be discussed. Whether the 220 t of section 1.1 is a model change, a configuration change or a different seed must be visible from the run records, not from someone's memory.

The simulator answers these risks with an architecture: a discrete-event engine with a fixed ordering rule, module adapters cut along the handbook architecture, a checked dependency graph, and a run configuration with a hash of every event log. None of this makes it a safety tool: the simulator is not safety-certified, a passing run or test campaign demonstrates model logic only, and no result is a basis for operational decisions. A rehearsal in it supplements, and never replaces, site training and authorisation (ch-16-09).

3. Terminology and foundations

ReferenceShow section 3

Discrete-event simulation. A simulation in which the model state changes only at discrete event times; between two events nothing changes, so the simulation clock jumps from one event to the next. ahs_sim.queueing.simulate_loop (ch-01-05) was already a small discrete-event simulation of one loading loop; the engine of this volume generalises it to the whole mine.

Fixed time-step simulation. A simulation that advances the clock by a constant step Δt and updates every model at every step. The dynamic truck model of ch-07-01 (ahs_sim.dynamics) integrates the equation of motion this way with 0.1 s steps.

Simulation clock. The engine's current time, in seconds of site time from 06:00 on day 0 [H]. It never runs backwards; an event may be scheduled at the current time or later, never earlier.

Event. One scheduled occurrence: time, priority, insertion sequence, kind, source, target and payload. Kinds of the handbook event schema (ch-22-01) are logged as telemetry records; kinds starting with an underscore are internal and only dispatched [H].

Event queue and deterministic tie-breaking. The engine keeps events in a priority queue ordered by the key (time, priority, insertion sequence), so the order of simultaneous events depends only on the inputs [H].

Entity. A simulated thing with a state history: a truck, a shovel, a plant, a light vehicle, a permission, a role.

Module adapter. The code that connects an earlier-volume module to the engine, declaring its inputs, outputs, emitted kinds and coupling level [H].

Coupling level. Wrapped run — a whole-shift model runs once and its results become engine events; event-level — the adapter reacts to engine events one by one; stub — scripted behaviour behind the same interface [H].

Run configuration and run hash. The run configuration lists what makes a run reproducible: reference-mine version, seed, module versions, scenarios and options. The run hash is a SHA-256 digest of the canonical event log (ch-22-01 schema, times rounded to 10⁻⁶ s) [H].

Reproducibility. The same configuration on the same code produces the same event log (equal run hashes). It is not evidence that the simulator is right.

Scenario runner and scenario request. The scenario runner (ahs_sim.scenario_runner) turns a scenario request (scenario ID, shift, fleet state, injected events, outputs, seed) into a plan, runs it on the engine and returns the log, KPIs, timeline, run hash and configuration [H].

Scripted decision policy. The representation of a person in the simulator: a role performs a step a fixed, assumed time [A] after the event it depends on. It is not a model of human performance.

The simulator is neither a digital twin, which is synchronised with the mine (ch-12-10), nor a training system that reproduces control-room functions (ch-16-09); it is an educational model with no link to the mine.

4. Technical explanation

4.1 Event-driven or fixed time step

The reference mine is a system in which most things are steady most of the time. DT17 hauls up R05 at a constant 11.4 km/h for 421 s (ch-01-01); between leaving EX02 and arriving at C01 nothing in its state changes that a production question cares about. What matters happens at the boundaries: arrival at a queue, start of Spotting, end of loading, a reservation granted, an alarm, a message received.

A fixed time-step design visits every truck at every step and asks whether anything has changed. LAB-23-01-01 runs DT17's M-20481 cycle both ways. The phases from haul_cycle.compute_cycle are 35 s Spotting at EX02, 132 s loading, 803.96 s travel loaded, 40 s Spotting at C01, 50 s tipping and 503.11 s travel empty, 1564.06 s in all (steady-state model, ch-01-01). In a fixed-step loop a phase ends at the first step at or after its true end, so every phase is rounded up to a multiple of the step:

Model conditions (section 4.10): the six phases of model M1 (haul_cycle.compute_cycle) run through the engine and through lab-local fixed-step loops (LAB-23-01-01); one truck (DT17, EX02 → C01); one cycle; queues none; acceleration none; disturbances none; deterministic, no seed. The shift column counts 40 trucks × 12 h for the loops and the events of the SCN-BASELINE-SHIFT log (seed 0) for the engine.

The engine reproduces the closed-form cycle to floating-point precision with 15 events per cycle. The 1 s loop needs 1565 steps per cycle, is still 0.94 s off, and visits trucks about sixty times more often per shift than the engine processes events.

The fixed time step is not wrong; it answers a different question. When the question is how speed changes inside a phase — acceleration out of a corner, a stop on a grade, a speed trace after a remote stop — the state changes continuously and a fixed step is the natural method; ch-07-01 finds the dynamic model 28.2 s (1.8 %) slower on M-20481. The simulator therefore combines the two [H]: the engine is event-driven, and an adapter may call a time-stepped model inside one event. The VCS adapter calls dynamics.stop_on_grade (0.01 s steps) and schedules one stop event at the computed standstill time. Events also fit the subject: messages between FMS, AMS and trucks are discrete, and the event log of Volume 22 is a list of discrete records that the KPI pipeline of ch-22-06 can read.

4.2 The engine loop and deterministic tie-breaking

FIG-23-01-02 shows the loop of engine.Engine [H].

Adapters and the scenario runner schedule events; the queue orders them by (time, priority, insertion sequence). The engine pops the first event, advances the simulation clock to its time, appends a telemetry record to the event log if the kind belongs to the event schema, and dispatches the event to every adapter whose inputs include its kind, in the order the adapters were registered. Each adapter may change entity states and schedule new events at the current time or later. The loop ends when the next event lies beyond the requested end time; the event log is then hashed.

Four rules keep the run deterministic [H]:

  1. The queue key is total. Time, then priority, then an insertion counter, so events at the same time and priority keep the order in which the inputs scheduled them.
  2. The clock never runs backwards. Scheduling before the current time, or at a NaN time, raises an error.
  3. Adapters are called in registration order. The scenario runner registers the wrapped shift log first, then the recipe's adapters, then the procedure.
  4. Randomness only through seeded generators. Every stochastic model takes an explicit seed (ahs_sim.rng); the seed is part of the run configuration.

Priorities carry a convention: a record that describes a state change an adapter has just made is scheduled at priority −1, so it is logged before other events at the same instant that depend on it (a cycle_state before the next truck's reaction); a vehicle-side brake command from an independent path is scheduled at −2, ahead of everything else at that instant. Priorities never change the time of an event, only the order within one instant.

LAB-23-01-01 lets DT17 and DT18 reach EX02-Q at the same instant. With DT17 listed first, DT17 is served first and DT18 queues for 167 s; with the list reversed, DT18 is served first. Both runs repeat exactly and their hashes differ: the list order is an input, and the rule makes its effect repeatable. A lab-local queue that breaks equal keys by a random draw serves DT17 first under three tie seeds and DT18 under three others, giving six different logs that nothing in the configuration explains. The rule does not make the order correct: which truck a real loading unit should serve first is a loading question (ch-13-02). Determinism makes the model's choice visible; it does not choose for the mine.

4.3 Module boundaries mirror the architecture

FIG-23-01-01 shows the simulator's parts. At the top, a scenario request goes to the scenario runner, which returns a scenario result. In the middle, the engine core holds the clock, the queue, the entity registry, adapter dispatch, the event log and the hash. Below it the module adapters are grouped like the handbook architecture: the FMS–AMS–ADS–VCS chain, the supporting elements outside the chain, and the site, network and fleet models.

The grouping is not decoration; it carries the authority rules of ch-01-04 into the code [H]:

Thirteen adapters: nine event-level, three wrapped runs, one stub (engine.adapter_catalogue()). Note what is absent. No FMS adapter handles a brake command. The AMS adapter can withhold a reservation and hold a truck, but has no input that clears a vehicle-side stop; the ADS adapter refuses an AMS resume while a vehicle-side cause is active and logs the refusal as an alarm. The independent safety function acts on its listed trucks after its own latency without consulting the AMS or ADS adapters. The onboard safety-related system raises its alarm and commands a controlled stop whatever the network state. These are the boundaries of ch-01-04, expressed as the absence of an input.

One simplification goes with the table: the event schema of Volume 22 has no source for independent safety functions, onboard safety-related systems, manned-vehicle devices or people, so the engine logs their records under CONTROL_ROOM or VCS and keeps the element in the payload [H].

4.4 The adapter interface and stubs

DetailShow 4.4

Every adapter implements the same small protocol [H]:

  • name, element, coupling — identity, architecture element and coupling level;
  • inputs — the event kinds it handles ("*" for all);
  • outputs — the entity states or results it writes;
  • emits — the event kinds it schedules;
  • attach(engine) — called once when the adapter is added; a wrapped-run adapter runs its module here and schedules the results; an event-level adapter registers its entities and first events;
  • handle(event) — called for each event whose kind is in inputs.

An adapter never calls another adapter; it only schedules events. That makes adapters replaceable: any object with the same name and declared interface can take an adapter's place.

The coupling level matters for interpretation. The FMS shift log is a wrapped run of one fms.simulate_fleet run (through telemetry.synthetic_shift): truck-level stops and holds are overlaid on each truck's own timeline without re-simulating the other trucks' queues, and holds that an event-level recipe adds later (a permission, a remote stop) are counted but not fed back into the fleet log. An event-level adapter interacts with other adapters event by event, the closest the simulator comes to integration in the full sense. A stub reproduces an interface without the behaviour behind it.

engine.StubAdapter takes an adapter's name, element, inputs and emits; it records what it receives and emits nothing, or a scripted response per input kind. engine.replace_adapter(name, stub) puts it in place before the run. Section 6.3 replaces the AMS adapter of the cancellation chain this way. A stub is a test instrument that isolates the part under test; it is not a model of a failed AMS, whose behaviour is a subject of its own (ch-02-08).

People are represented by the one adapter that is a stub by design. ProcedureAdapter takes key steps, each naming an actor, an element, the step it follows and a delay [A]; a step that needs the field data link waits until the link is back or an alternative path such as the radio is available. For registered scenarios without a specific model the delays are the gaps between the registry's key events, so such a run reproduces the registry timeline by construction (section 4.7).

4.5 The dependency graph

DetailShow 4.5

Integrating fifty modules can fail in two ways the separate modules could not: an import cycle, which makes a module's meaning depend on load order, and a plotting import in the engine, which makes batch runs need a display. Two rules prevent this [H]: the module-level import graph of ahs_sim is acyclic, and ahs_sim never imports ahs_sim_viz, matplotlib or a GUI library (the same check as tools/validate.py sim-deps).

engine.check_dependencies() reads the source with Python's ast module, without importing anything, and builds the graph. LAB-23-01-02 finds 50 modules and 159 module-level imports; the graph is acyclic and free of visualisation imports. FIG-23-01-03 shows the part of it around the engine and the scenario runner.

Three properties are worth checking by eye. The engine core (_eng_core) imports only the event schema _tel_schema at module level; everything domain-specific sits in the adapters. No earlier-volume module imports the engine or the runner, so the models of Volumes 01 to 22 keep the meaning their chapters gave them. And ahs_sim_viz imports ahs_sim (dashboard → analytics, network plot → mine), never the reverse.

One cycle remains, and it is reported rather than hidden. telemetry imports _tel_shift at module level, and _tel_shift imports telemetry inside a function. A function-level import runs only when the function is called, after both modules are loaded, so it cannot cause an import-time failure; the check lists it separately as a deferred cycle. It is still a cycle in the design: the two modules cannot be tested entirely apart. The engine's own deferred imports (_eng_core reads the package version, mine and paths inside default_config; _eng_adapters loads _tel_shift, energy and reliability inside the adapters that wrap them) close no cycle. Removing the _tel_shift ↔ telemetry cycle means moving the shared names into a third module; until then the deferred-cycle list keeps it visible.

4.6 Reproducibility: configuration, seed, versions and run hash

A run is reproducible when everything that influences its event log is either fixed by the code or written in its configuration. engine.RunConfig records [H]:

Field Baseline value Why it is needed
Mine version 0.3.0 geometry, speed limits, areas and equipment come from mine.yaml
Seed 0 every random draw comes from seeded generators
Module versions ahs_sim 0.25.0, telemetry schema 1.0, scenario registry schema 1 the models, the record format and the registry format
Scenario IDs SCN-BASELINE-SHIFT what is injected
Options shift, request, injected scenarios everything else the recipe uses

The configuration has its own hash; changing the seed changes it. The run hash is SHA-256 over the event log: one canonical line per record (fields in schema order, times rounded to 10⁻⁶ s, payload as sorted JSON), in log order.

LAB-23-01-02 runs SCN-BASELINE-SHIFT through the scenario runner. With seed 0 the log has 28,650 records and the run hash begins 6a578f1729cfc5f2; a second run with the same request gives the same hash. Seeds 0 to 4 give five different hashes and 183,920 to 185,680 t. The planner's two runs in section 1.1 (184,140 t and 184,360 t) are seed 0 and seed 1 of the same model: a replication, not a change. The fleet behind these tonnes is model M6 of section 4.10 (37 producing trucks, queues, service and travel variability, no acceleration). Changing one dump record's time by one millisecond, or swapping two records, also changes the hash.

The hash covers the log, not the configuration: the rehearsal of section 8.3, with an explicit fleet state equal to the defaults, gives the same run hash as the default request, while the configuration hashes differ. It is order-sensitive, as determinism requires. And it is exact: it says whether two runs are identical, not whether they are close; tolerances belong to the regression suite of ch-23-10.

The configuration holds version strings, not content: if mine.yaml were edited without a version change, two runs with the same configuration would read different geometry. It does not hold the Python or library versions either; the pinned environment of make setup covers them in practice, but the run record does not show it. LAB-23-01-02 prints content fingerprints of the four shared files a run reads; REQ-23-01-004 asks for both kinds of record.

Comparability. Two results may be used together in a discussion only if they come from comparable runs [H]: same mine version, same module versions, same scenarios and same options. A different seed is allowed and marks a replication, to be compared with intervals rather than single values (ch-23-10). engine.comparable implements the rule. On two configurations from default_config with seeds 0 and 1 it returns "comparable, seeds differ". On the summaries of two run_scenario runs with seeds 0 and 1 it returns "not comparable": the runner stores the whole request, seed included, in the options, so the seed is counted twice. With the seed removed from the embedded request (LAB-23-01-02) the answer is "comparable, seeds differ"; a changed mine version or fleet state stays "not comparable".

run_scenario returns a ScenarioResult whose summary() holds the scenario, status, configuration, run hash, KPIs, timeline verdict and limitation. A registry key event passes if it was simulated, lies within max(10 s, 25 % of its registry time) [A] and does not come before the steps that precede it.

The runner covers every registered scenario, but not equally. limitations_register() lists the 65 scenarios of the registry. It flags 64 as registered: for SCN-FIRE-DT17-COMMS (fire on DT17 during a CT3 outage, ch-23-09) the runner composes its own timeline and still sets registered=False, a known limitation. Fifteen run end to end. Six run partially with a scenario-specific model recipe. Forty-four run with the default recipe: the baseline shift plus the registry key events scripted with the registry's own gaps as response times. For those 44 the timeline check passes by construction: the times compared are the times that were scripted. Such a pass shows only that the scenario is wired into the runner, so a timeline pass is always quoted with its group.

4.8 People as scripted decision policies

DetailShow 4.8

In the simulator, the AHS Controller, Pit Supervisor, Shovel Operator, ERT and Survey do not decide. They perform scripted steps at assumed times [A]: the controller acknowledges an alarm 5 s after it appears, the ERT arrives at the zone boundary after a stated travel time, the Pit Supervisor confirms an area clear at the registry's time. The values sit in scenario_runner.RESPONSE_S or in a chapter's lab, each one tagged [A].

The handbook has no validated model of human behaviour, and an invented one would look more authoritative than it is. A scripted step makes the assumption visible and changeable. In the cancellation chain the controller's radio call is one step at T+5 s, taken from ch-01-04; nothing says a controller should take 5 s, and simulated response times are not performance standards. A step that depends on a system waits for it, which is what a rehearsal of a communication loss needs to show (ch-23-09 explores SCN-FIRE-DT17-COMMS, a fire during the CT3 outage).

4.9 Trade-offs and model limits

DetailShow 4.9
  • Event-driven core, time-stepped detail inside single events where motion is continuous.
  • Wrapped runs for scale, event-level for interaction. One fleet-model run per shift is cheap and verified; holds added later do not reshape the other trucks' queues.
  • Strict determinism, explicit randomness. Variation comes only from seeds; a result shown alone is one draw.
  • Exact hash, separate tolerances. Whether a change matters is decided by the regression tolerances of ch-23-10.
  • No middleware, no game engine. The engine is a few hundred lines of Python on the standard library; robotics middleware or a 3-D environment would add infrastructure without a learning objective that needs it.

Read down the table, one condition at a time [A] (all values from the lab, none fitted):

  • M1 to M2: acceleration. Accelerating and braking add 28.2 s per cycle. Both still fit 27 whole cycles into 12 h (27 × 1564.1 s = 42,229.6 s; 970.4 s of the shift are left over), so loads per truck do not change and the time per load is 1600 s in both.
  • M2 to M3: the live truck. Alone at its loading unit, a live truck needs 39.5 to 102.2 s more per cycle than M2: corner speed caps at every interior node of its route, speed control with actuator lag, a granted path extended block by block and varied service times. The lab does not separate these causes.
  • M4: the fleet without queues is not possible. Summing M1 over the 37 producing trucks gives 909 loads, but EX01 would need 45,090 s of Spotting and loading and C01, with one tipping position, 46,170 s of Spotting and tipping in a 43,200 s shift. Queues must form.
  • M4 to M5: queues. With queues the fleet delivers 869 loads. C01 tips 469 ore loads, 42,210 s of its 43,200 s: ore is limited by the crusher, not by the trucks, and EX02's time per load rises to 1743 s.
  • M5 to M6: variation. Varied service and travel times (seed 0) cost 32 loads more, 837 loads or 184,140 t, with 89.5 s of queue per load at the loading units. Other seeds give 183,920 to 185,680 t (section 4.6).
  • M6 to M7: the live world, same fleet. The same 37 trucks deliver 757 loads, 166,540 t, 9.6 % less. C01 receives 392 ore loads, one every 110 s on average against one every 96 s in M6, because a live tipping slot is held from the truck's admission onto the last lane block until dumping ends, and trucks drive as in M3. The queue at the destinations grows from 68.7 to 207.4 s per load.
  • M7 to M8: three more trucks. The UI's 40 trucks add ECO-01 to ECO-03 at EX01, EX02 and EX03 (the live world's allocation, not DT29, DT39 and DT40). They add 18 loads, 17 of them waste: C01 receives 393 ore loads, one more, so the extra ore trucks only queue (310.4 s per load at the destinations) and EX02's time per load rises to 2298 s.

So the 1564 s cycle, the fleet's 184,140 t and the live world's 166,540 or 170,500 t are not an error and its correction. Each answers its own question: the cycle of one truck on an empty mine; a shift with queues and variation but steady speeds; a shift with motion, traffic and admission to service positions. A number is quoted with its row, and a difference between two numbers is explained by the conditions that differ before anyone calls it a discrepancy (REQ-23-01-006).

6.2 Abnormal operation: a duplicated cancel and a run that does not repeat

DetailShow 6.2

At T+5 s the FMS sends the same cancel again, with the same key [A]. The AMS adapter receives it at T+5.3 s, the mission state machine (ahs_sim.mission) discards it as a duplicate at T+6.0 s, and nothing else changes: same release times, same stop, HOLD_LOADED at T+103.3 s. This is the abnormal case for the simulator itself. The hash says "different run"; the outcome says "same rehearsal". Both are right: the hash answers the reproducibility question, the outcome the rehearsal question, and neither says the model is right. A run that unexpectedly does not repeat is traced through its summary in this order: configuration (mine version, module versions, scenario, options, injected events), seed, then the log. Here the injected duplicate explains the difference.

7. Engineering view

DetailShow section 7 (7.1 Design decisions and trade-offs; 7.2 Failure modes and mitigations; 7.3 Interface and timing considerations)

7.1 Design decisions and trade-offs

Event-driven, with time-stepped calls inside events. The cost is that continuous behaviour must be summarised as events: the cancellation chain has no deceleration phase, and a speed trace needs the time-stepped model of ch-07-01.

One log, in the schema of Volume 22. Every logged event is a telemetry.EventRecord. The engine's KPIs therefore come from the same analytics.kpi_pipeline that ch-22-06 reconciles with ahs_sim.kpi; for the baseline the pipeline gives 184,140 t, 837 loads, Physical Availability 0.9487 and Production Effectiveness 0.6132, the values of ch-22-06. The price is that internal messages, such as PATH and PATH_ACK, are not in the log; the lab records them with an engine hook.

Adapters, not inheritance from the models. An earlier module is called, never modified. The cancellation chain calls ahs_sim.mission.Mission for the state machine and ahs_sim.ams.ReservationTable for the reservations; the state machine still enforces the idempotent cancel of ch-02-07 and ch-10-08 unchanged.

Three coupling levels, labelled. Coupling is declared on the adapter and reported in every result, so a reader of a result knows whether the fleet was re-simulated or overlaid.

Determinism over parallelism. The engine does not run adapters in parallel or batch events across time; both would make the order depend on scheduling.

7.3 Interface and timing considerations

Lay the timeline of section 6.1 against the interfaces. The FMS–AMS interface carries four messages (cancel, ACK, accepted, complete) at T+0, 1.3, 4.3 and 103.6 s; the AMS–ADS interface carries one path and its acknowledgement at T+2.3 and 3.3 s; the ADS–VCS interface carries one brake request at T+102.3 s. In the engine each crossing is an event scheduled by the sender at the receiver's arrival time; the receiver's processing delay is another event, at which the state change happens. That is why the AMS adapter releases R21 not at T+3.3 s, when PATH_ACK arrives, but at T+4.0 s, after its 0.7 s processing (the example in FIG-23-01-02). An adapter that changed state on arrival and only recorded a later time would put the AMS state ahead of its own processing. Within one instant priorities order the work: at T+40.0 s the key event of the release is scheduled at priority −1, so it is logged before anything that reacts to the release.

The timing values are assumptions taken from ch-01-04 and ch-10-08; the engine adds none of its own. The simulator can show that the release follows the acknowledgement and precedes the stop under the stated assumptions. It cannot show how long a real AMS takes.

The runner's own recipe for SCN-MISSION-CANCEL-M20481 is a different, closed-form variant: DT17 at the middle of R01 stops at a hold line 30 m before X with comfort deceleration, and the reservations are released at T+32.1 s. Both variants reproduce the registry's key events within tolerance; the walkthrough of ch-01-04 and ch-10-08 is the one this chapter follows. A reader who compares the two must state which variant each number comes from.

8. Operations view

8.1 What the control room sees

The simulator has no HMI. An operations reader sees the timeline and the run summary. The timeline of the rehearsal shows the events of section 6.1 with the element that acted. It answers the rehearsal's questions as sequences: did cancelling come before accepted by vehicle, the hold only after DT17 cleared X, complete only after the truck stopped?

The run summary carries, for every run:

  • scenario ID and execution status (end to end, partial with a model recipe, or partial with scripted key events);
  • configuration: mine version, module versions, scenario, options (including the request), seed;
  • run hash;
  • KPIs (tonnes, loads, Physical Availability, Use of Availability, Production Effectiveness, unplanned stops, queue time per load);
  • timeline verdict and the recorded limitation.

Before two results go on one slide, check the two summaries line by line [H]: mine version equal; module versions equal; scenario and options equal (apart from the seed copied inside the request); seeds equal (same run) or different (replication: compare with intervals). For the planner's two baseline runs of section 1.1 the check reads: mine 0.3.0 and 0.3.0; ahs_sim 0.25.0, schema 1.0 and registry schema 1 on both; scenario SCN-BASELINE-SHIFT on both; options equal except the seed; seeds 0 and 1. Verdict: comparable, a replication. The 220 t difference is within the spread of seeds 0 to 4 (183,920 to 185,680 t) and shows no change in the model.

8.3 Procedure excerpt — requesting and reading a rehearsal

The AHS Controller asks for a rehearsal of the M-20481 cancellation.

  1. Controller: name the scenario by its registry ID (SCN-MISSION-CANCEL-M20481) and say what the rehearsal must show (the order of cancelling, accepted, hold and complete).
  2. Controller: state the shift (DAY), the trigger time (07:00, T+3600 s after shift start), the fleet state (40 trucks, fixed allocation), injected events (none) and the outputs wanted (timeline, KPIs, metrics).
  3. Controller: state the seed (0) or accept the default, so the run can be repeated.
  4. Site engineer: check the scenario's execution status in the limitations register and tell the requester if it runs only as scripted key events.
  5. Site engineer: run the request; record the configuration hash and the run hash with the result.
  6. Controller and Pit Supervisor: read the timeline against the purpose of step 1; note every response time that is an assumption (the controller's T+5 s radio call).
  7. Pit Supervisor: before quoting any number from the run in another meeting, compare its summary with the other run's (section 8.1).
  8. All: record that the rehearsal supplements, and does not replace, site training and authorisation (ch-16-09).

Steps 1 to 3 in the runner's form are LAB-23-01-02's REHEARSAL: it runs end to end, passes the timeline check and repeats to the same hash. The runner returns its closed-form variant (release at T+32.1 s, section 7.3); the chain of section 6.1 is the lab's own model.

The architecture itself moves no KPI. It decides where KPIs come from: the engine's event log through analytics.kpi_pipeline, so the time-usage KPIs follow ch-01-05 and ch-22-06. In the cancellation, DT17's hold at C01-Q is coded DLY-OD-10 from T+102 s while C01 is down (ch-01-04); the rehearsal chain of this chapter does not run the delay coding, which belongs to the fleet log. The simulator can help with sequence, timing under stated assumptions and the relative throughput effect of a scenario against the baseline of the same configuration. It cannot give safety assurance or forecast what any mine will produce.

8.5 Training and competency implications

DetailShow 8.5

People who request rehearsals need the scenario registry IDs, the fields of a scenario request, the three execution statuses and the comparability check of section 8.1, and should recognise every simulated response time as an assumption. 9. Requirements and acceptance criteria

ReferenceShow section 9

REQ-23-01-001 [H] The simulation engine shall order events by time, then by priority, then by insertion sequence, shall not advance its clock backwards, and shall reject events scheduled before the current time; equal inputs shall produce equal event logs. Rationale: an order that depends on anything outside the inputs makes runs differ without a configuration difference (section 4.2: six random tie seeds gave six logs). Verification: test (LAB-23-01-01 queue order and simultaneous arrivals; sim/tests/test_engine.py).

REQ-23-01-002 [H] Every module of an earlier volume shall be connected to the engine only through an adapter that declares its architecture element, coupling level, inputs, outputs and emitted event kinds; adapters shall communicate only by scheduling events and shall not call one another. Rationale: declared interfaces make each behaviour traceable to its source chapter and let a stub replace an adapter (sections 4.3 and 4.4). Verification: inspection of engine.adapter_catalogue(); test (LAB-23-01-01 with the AMS adapter replaced by a stub).

REQ-23-01-003 [H] No adapter representing the FMS or the AMS shall have an input that stops a truck directly or clears a vehicle-side stop cause; the ADS adapter shall refuse and log an AMS resume while a vehicle-side cause is active, and adapters for independent safety functions and onboard safety-related systems shall act without consulting the AMS or ADS adapters. Rationale: the simulator must teach the authority boundaries of ch-01-04, not contradict them (section 4.3). Verification: inspection of adapter inputs; test (sim/tests/test_engine.py, sim/tests/test_scenario_runner.py remote-stop and fire cases).

REQ-23-01-004 [H] Every run shall record a configuration with the reference-mine version, seed, module and schema versions, scenario IDs and options, and the hash of its event log; the record should also hold content fingerprints of the shared data files the run reads and the interpreter and dependency versions. Rationale: a version string does not detect an edited data file, and a result without its configuration cannot be reproduced or compared (section 4.6). Verification: test (LAB-23-01-02 identical hash on repeat, distinct hashes across seeds); inspection of the run record.

REQ-23-01-005 [H] The module-level import graph of ahs_sim shall be acyclic, ahs_sim shall not import a visualisation or GUI library or ahs_sim_viz, no earlier-volume module shall import the engine or the scenario runner, and every cycle that closes only through a function-level import shall be listed in the dependency report. Rationale: integration must depend on the models, not the reverse; a hidden deferred cycle is still a design coupling (section 4.5). Verification: test (LAB-23-01-02; engine.check_dependencies; tools/validate.py sim-deps).

REQ-23-01-006 [H] A simulation result shall be compared with another only if both share the reference-mine version, module versions, scenarios and options; results with different seeds shall be presented as replications with intervals, not as single values. Rationale: two runs of the same baseline differ by 220 t from the seed alone (sections 1.1 and 8.1). Verification: demonstration (LAB-23-01-02 comparability cases); inspection of review material.

REQ-23-01-007 [H] Every timeline result shall state the scenario's execution status (end to end, partial with a model recipe, or partial with scripted key events); a timeline pass of a scenario run with scripted key events shall not be presented as validation of the scenario's behaviour. Rationale: 44 of 65 scenarios pass by construction (section 4.7). Verification: inspection of reports; test (LAB-23-01-02 coupling counts; scenario_runner.limitations_register).

REQ-23-01-008 [H] A scenario request shall state the scenario ID, shift, fleet state, injected events, outputs and seed; the result shall return the request with its configuration and run hash. Rationale: with these fields an engineer can run the request without further clarification, and the requester can repeat it (section 8.3). Verification: demonstration (LAB-23-01-02 rehearsal request run twice, same hash).

REQ-23-01-009 [H] Every simulated human response time shall be a named parameter tagged as an assumption, and simulator results shall not be used as a performance standard for people or as a basis for operational decisions. Rationale: the handbook has no validated model of human performance; scripted policies make the assumption visible (section 4.8). Verification: inspection of scenario_runner.RESPONSE_S and lab parameters; inspection of reports.

Validation against registry timelines is the work of ch-23-04 to ch-23-10, reported in ch-23-10. Both scenarios of this chapter run end to end and pass their timeline checks. 11. Common mistakes

DetailShow section 11 (11.1 Design mistakes; 11.2 Operational mistakes)

11.1 Design mistakes

  • Choosing a fixed time step for whole-shift runs because it is easier to write. It costs 1,728,000 truck-steps per shift at 1 s and still leaves an error; use events and call time-stepped models inside events.
  • Breaking ties by set order. Python's set order for strings changes between processes; use an explicit insertion counter.
  • Letting an adapter call another adapter. It works until someone replaces one of them with a stub. Communicate through events.
  • Changing state on message arrival and logging a later time. The state is then ahead of its own processing (section 7.3).
  • Putting domain rules in the engine. A permission rule in the engine cannot be traced to ch-10-06 or stubbed.
  • Importing plotting code in an ahs_sim module "for a quick check". Put it in ahs_sim_viz.
  • Hiding a deferred import cycle because the module-level check passes. List it and plan its removal.
  • Recording only version strings. An edited mine.yaml without a version change goes undetected.

11.2 Operational mistakes

  • Comparing two results without comparing their summaries. The planner's 220 t was a seed, not a change.
  • Reading a timeline pass as proof for a scenario that runs as scripted key events.
  • Quoting a simulated response time as a target ("the controller should acknowledge in 5 s"). It is an assumption.
  • Requesting "run the fire scenario" without ID, shift, fleet state and outputs; the result cannot be repeated.
  • Treating a rehearsal as training credit. It supplements site training and authorisation; it does not replace them (ch-16-09).
  • Using a simulated tonnage as a forecast in a production meeting. The simulator gives relative effects under stated assumptions.

12. Worked examples

DetailShow section 12

Example 1 — event-driven against fixed step. 35 + 132 + 803.96 + 40 + 50 + 503.11 = 1564.06 s (steady-state model). With Δt = 1 s: 35 + 132 + 804 + 40 + 50 + 504 = 1565 s (+0.94 s, 1565 steps) against 15 events; over a shift 40 × 43,200 / 1 = 1,728,000 truck-steps against 28,659 events.

Example 2 — tie-breaking. Events _b at 10 s (priority 0), _a at 5 s (0), _c at 10 s (−1), _d at 10 s (0), inserted in that order, come out as _a, _c, _b, _d.

Example 3 — can DT17 accept the shortened path? At T+2.3 s DT17 is at 50 + 13.89 × 2.3 ≈ 82 m past P1, with 1,246 m from its T+0 s position to C01-Q minus 32 m travelled, about 1,214 m. At 50 km/h (13.89 m/s) and 0.8 m/s² [A] it needs 13.89² / (2 × 0.8) = 120.6 m. It accepts; PATH_ACK reaches the AMS at T+3.3 s and R21 is released at T+4.0 s.

Example 4 — reading two summaries. Run A: mine 0.3.0, ahs_sim 0.25.0, SCN-BASELINE-SHIFT, seed 0, 184,140 t. Run B: same, seed 1, 184,360 t. Comparable as a replication. Five seeds give 183,920 to 185,680 t, a range of 1,760 t; the 220 t between A and B is inside it. Run C: same as A but fleet state 38 trucks: not comparable with A as a replication; it is a different question, and its effect must be estimated with replications of both.

Example 5 — execution status. Of 65 scenarios, 15 end to end + 6 partial with a model recipe + 44 partial with scripted key events = 65. A report that says "the suite passes 65 of 65 timelines" without the split overstates what was shown by the 44 scripted ones.

15. Key takeaways

  • The integrated simulator is event-driven: the clock jumps between state changes; time-stepped models run inside single events where continuous motion matters.
  • Events are ordered by time, priority and insertion sequence; equal inputs give equal logs, and a list order is an input.
  • Adapters mirror FMS, AMS, ADS, VCS, independent safety functions, onboard safety-related systems, manned-vehicle devices and people; they communicate only through events, declare their coupling, and authority boundaries appear as inputs an adapter does not have.
  • The module graph is acyclic and free of visualisation imports; one deferred cycle (_tel_shift ↔ telemetry) is listed, not hidden.
  • A run is reproducible from its configuration (mine version, seed, versions, scenarios, options) and identified by its run hash; the configuration should also record data content and environment.
  • Compare results only when their summaries match; different seeds are replications.
  • People are scripted decision policies; every simulated response time is an assumption, and no result is a basis for operational decisions.
